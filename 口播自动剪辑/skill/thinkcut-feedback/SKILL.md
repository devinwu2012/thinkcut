# 反馈（thinkcut-feedback）

> **路径和 IP**（2026-11-24 配置档）：下文 `$AI` 是程序目录：`AI=$(cd -P ~/.claude/skills/thinkcut-feedback/../../.. && pwd)`（技能链接指着的使用版；在开发版试验时换成开发版目录）。`<片子文件夹>`、`<试验田>`、`<回收站>` 是这个 IP 配置的位置，用 `python3 "$AI/bin/cutdesk_config.py" show --key 片子文件夹` 查（默认是程序目录旁边的 `<IP 名>视频/`、`<IP 名>试验田/`、`#recycle/`）。做哪条片子先读它所属 IP 的规矩：`python3 "$AI/bin/cutdesk_config.py" rules --project <项目根>`（在 `配置档/<IP>/规矩.md`），和这里冲突时以那份为准。


**2026-11-22 用户改了做法**：“反馈完就是反馈，直接反馈到总AI里，把问题给到总AI，总AI根据整个全局的情况来看是否要修复，或者反馈到这个项目里。要不然每次对话里反馈好几轮，很麻烦。”所以：**做片子的会话只整理、直接交，不在对话里列清单、不逐条问、不发定稿表**；架构审查看全局决定每条改不改、怎么改，要用户拍板的由架构审查攒到一次问。（以前 11-11 定的“列清单给用户勾选确认再交”作废。）2026-11-11 用户定不做每日复盘，**按项目复盘**：每条片子做完交一次反馈单，架构审查复盘一次。闭环：**做片子随手记 → 反馈时先回查上次的修改 → 列新问题直接交 → 架构审查看全局定、改、写验收标准 → 下一条片子再回查**，每条片子记 3 个数看回路有没有起作用。

**谁改什么**：用这个技能的会话只整理、交反馈单，**不改 `$AI` 里的任何东西**（程序、说明、花字库、音效库、问题台账）；改能力和台账只由架构审查做。唯一例外是第 5 步：用素材库命令把本期素材说明写进素材库索引（只写数据，不改程序和说明）。

**两个文件**：
- 片子里的 `<项目文件夹>/02_制作/反馈记录.md`：做片子时随手记（规则在每个项目的 AGENTS.md），反馈时以它为主、对话为辅。
- 总账 `$AI/内部/经验/问题台账.md`：每个问题的编号、修法、验收标准、状态。只读。

## 0. 回查上次改过的

读问题台账里状态是“已改·待验证”和“复发”的条目，按各自的**验收标准**在这条片子上查（看反馈记录、对话、`合成/自检结果.json`、成片响度、SRT 条数、job.json 等，能跑命令量的就量）。每条标：

- **已验证**：这条片子用到了，验收标准达到；
- **复发**：又出现了（写清在哪、用户原话）；
- **没用到**：这条片子没走到那一步，下次再查。

复发的放进第 1 步清单最前面，建议的修法要比上次的更硬（上次写进说明的改成自检或硬拦，上次是自检的改成硬拦或程序自动做）。回查时特别看这几类：给用户写了 MD（Q016）；用户不在场（“中途不要停下来问我”）时自己记“用户确认”、没让用户真看过（Q023/Q025，查 `words` 和确认记录里有没有“用户未逐张看”）；音效、大字没卡在词上（Q005）；标题简介标签没出文案让用户选（Q034）。

## 1. 整理新问题清单

以 `02_制作/反馈记录.md` 为主，再从会话开头读到现在补漏，找出：

- 用户纠正、返修的地方（照抄用户原话）；
- AI 判断错、跳过了技能里的步骤；
- 工具报错、慢、要手动补、绕了远路（命令和报错原文）；
- 用户新定的规矩（原话，注明“以后都这样”还是“只这条片子”）；
- 用户在达芬奇里手改了 AI 的结果。

只这一条片子的事（改一个字、换一张图）不列，除非背后是能改能力的规律。台账里已有的问题不新开，写成“Qxxx 又出现”。

每条写清：

- 发生了什么（用户原话照抄）、谁先发现、建议怎么改（标“AI 建议”）、修法级别、验收标准、是不是用户亲口定的规矩。
- 例：新1（剪口播）气口没精修就建了审核线，用户：“气口不干净”；用户先发现；AI 建议：建审核线前拦 ≥0.27 秒停顿（硬拦）；验收：建审核线时 0 处。

- **分项**：剪口播 / B-roll / 动画成片 / 花字音效 / 字幕导航 / 审核线 / 导出 / 封面 / 上传 / 项目 / 沟通 / 其他。
- **谁先发现**：用户 / AI自查 / 工具拦下。
- **修法级别**从硬到软：程序自动做 ＞ 硬拦 ＞ 自检报警 ＞ 写进说明。**用户先发现的，修法不能只是“写进说明”**（2026-11-01 气口：规矩早写了，照样被跳过）。规则已经有、这次没照做的，方案写“加检查、做成硬拦”，不再写一遍规则。
- **验收标准**：下一条片子上怎么判断修好了，要能查、能数（“0 处”“≤ -1 dBFS”“用户没再说××”）。
- **用户亲口定的**（用户说了“以后都这样”、或直接说了要怎么改）照原话写成“用户定的”；其余都是“AI 建议”，由架构审查定。
- 和已定规矩冲突的单独标“冲突：原来定的是…”，交给架构审查去和用户确认。
- 只影响这一条片子、不该改能力的，也写上，标“可能只是这条片子的事”，由架构审查决定是回给这条片子的会话去改，还是改能力。

## 2. 不在对话里确认（2026-11-22 起）

不发清单表、不用选项问、不发定稿表、不问“这样交给架构审查？”。整理完直接写反馈单交出去（第 4 步）。清单和细节只写在反馈单里，给架构审查看；用户想看再给路径。

## 3. 记 3 个数

数 `反馈记录.md`（没有就从对话数）：

- **审核轮数**：用户在时间线（或网页）完整看过、提意见的轮数；
- **用户先发现**：用户先指出的问题条数；
- **AI 自查先发现**：AI 交审前自己查出、在用户之前修掉的条数。

写进反馈单开头和片子复盘开头。

## 4. 交给架构审查

1. **写反馈单**：`$AI/内部/经验/待审/YYYY-MM-DD_<片名或主题>_反馈单_<反馈人>.md`（反馈人用片子所属 IP 配置的 `反馈人`：`python3 "$AI/bin/cutdesk_config.py" show --key 反馈人 --project <项目根>`，不用问用户，2026-11-01 用户定）。格式：

   ```markdown
   # 反馈单：<片名或主题>（YYYY-MM-DD）
   反馈人：<反馈人>   来源会话：<会话名>   片子目录：<项目文件夹或“无”>
   3 个数：审核 N 轮；用户先发现 N；AI 自查先发现 N
   以下条目由做片子的会话整理，没和用户逐条确认（2026-11-22 用户定：直接交给架构审查看全局决定）；“用户定的”是用户原话，其余是 AI 建议。

   ## 回查
   | 台账编号 | 结果（已验证/复发/没用到） | 依据 |

   ## 问题
   ### 新1. <一句话问题>（分项；或“Q003 复发”）
   - 发生了什么：……（用户原话：“……”）
   - 谁先发现：……
   - 用户定的：……（用户原话；没有写“无”）
   - AI 建议：……（修法级别：……；改哪里：……）
   - 验收标准：……
   - 备注：冲突／可能只是这条片子的事／其他（没有写“无”）

   ## 相关文件
   - 反馈记录、片子复盘、自检结果等路径
   ```

   写反馈单不用占位、不跑测试、不提交。

2. **发消息**：用 SendMessage 发给会话 `架构审查`（ListAgents 里名字带“架构审查”或“项目审查”的会话）：第一行“反馈单：<片名>，N 条问题，回查 N 条（复发 N）”，第二行写反馈单路径。发不出去（Codex 会话，或架构审查会话没开）就告诉用户：在“架构审查”会话里说“处理反馈单”。

3. **告诉用户**（第 5 步做完后一起说，**一两句话就够**）：“交了 N 条给架构审查（其中复发 N 条），素材库写了 N 条；反馈单在 <路径>。”不在对话里列表、不问问题。

## 5. 素材写进素材库（2026-11-12 用户定）

做这条片子的会话最清楚每条素材是干嘛的，收尾时由它直接写进素材库，不等别人事后看图猜。片子没有 01_原始素材（不是标准项目）就跳过这一步。

1. `python3 $AI/口播剪辑/bin/library.py notes-template <项目文件夹>`：先更新这一期的索引，再生成 `02_制作/素材库说明.json`，里面列出本期全部 A roll、B roll 和每个动画镜头（代码动画、Blender、Remotion、卡片合成），附现在的描述、用在哪句口播、动画工程候选。
2. 按文件里的 instructions 逐条填 description、tags、usage_note（讲什么、以后适合配什么口播）、notes（水印、露人、镜像、只有前几秒能用等），素材补 shots（自动没对出来的镜头号），动画写 tool（真正做出这一镜的工程文件夹）。依据是这次会话的实际经历和用户说过的话，不照搬看图描述。
3. `python3 $AI/口播剪辑/bin/library.py notes <项目文件夹>`：全部合格才写入，报错就按提示改了再跑。写进去的说明优先于看图补写和素材清单说明。
4. 素材清单里没登记的素材（比如群聊照片）先按 thinkcut-project 登记，再重跑第 1 步。

## 片子做完时

片子收尾（thinkcut-edit 第 7 步）＝ 先写片子复盘（[片子收尾.md](../thinkcut-edit/references/片子收尾.md) 第 1 节），再按本技能 0–5 走；复盘里的“动画清单”作为一条“合进动画案例索引”放进清单。片子没做完也可以随时反馈，写到哪一步算哪一步，回查只查走到了的步骤。

## 架构审查收到反馈单后（按项目复盘）

- **看全局逐条定**（2026-11-22 用户：“总AI根据整个全局的情况来看是否要修复，或者反馈到这个项目里”）：每条定成一种——
  - **改**：用户定的照做；AI 建议的按台账里同类问题、已有程序和规矩，选最省事、最硬的修法（可以和建议不一样）。
  - **并进已有条目**：台账里已有的同类问题，记“复发”或补进那条，不新开。
  - **回给这条片子**：只影响这一条片子的，不改能力，用 SendMessage 告诉原会话该怎么改（原会话没开就写进汇报）。
  - **不改**：写清理由（已有程序拦着、一次性的、和别的规矩冲突又不值得改等）。
  - **要用户定**：只有这几种——用户定的和已定规矩冲突、要删用户数据、业务或审美上的取舍、改动很大。攒到一起，在架构审查会话里用选项一次问完，不一条条问。
- 按改到的文件夹各自的 AGENTS.md：占位 → 改 → 测试（能在达芬奇或真片子数据上实测的就实测）→ 升版本、写更新记录（根目录 `VERSION`、`CHANGELOG.md`，全家一份）→ 存档（整个程序目录一个仓库）→ 删占位。
- **更新问题台账**：
  - 回查结果：已验证的改状态、写“最近检查”；复发的次数加一、状态改“复发”，按反馈单换更硬的修法后再改回“已改·待验证”。
  - 新问题编新号（Q 接着往下编），填修法级别、改在哪（版本）、验收标准，状态“已改·待验证”；暂缓的状态写“暂缓”。
  - 用户先发现、修法只有“写进说明”的，标“待升级”。
  - “每条片子的 3 个数”表加一行。
- **顺带做一次项目复盘**（取代原来的每日复盘）：
  - 两个待审目录（`口播剪辑/经验/待审/<分项>/`（旧的，只在 NAS 上）、`内部/经验/待审/`，`_已处理/` 除外）里还没处理的其他经验，汇总给用户定；
  - 开发版仓库（2026-11-24 起整个程序目录一个仓库）有没有未存档的改动、残留的 `正在修改中.txt`；
  - 有没有新出现把片子或程序的东西存到这台 Mac 的代码或说明（允许的例外：`~/Library/Application Support/ThinkCut/环境` 运行副本、`~/.claude/skills` 和 `~/.codex/skills` 里指向 NAS 的技能链接）；
  - 台账里“待升级”的还有几条。
- 改完：反馈单移进 `内部/经验/待审/_已处理/`，`内部/经验/已采纳.md` 记一笔；回消息给原会话（还开着的话）；向用户汇报一次：每条怎么定的（改／并进／回给片子／不改，各几条，不改的一句理由）、版本号、回查结果、哪些还没验证、3 个数和上一条片子比是多了还是少了。
