# 口播自动剪辑（`studio/`）：给 Codex 与 Claude Code 的说明

这里是 NAS 上集中维护的口播成片能力，包括脚本、Skill、动画模板和样例。它不是成品目录：两台 Mac 共用这份代码，每个项目的中间文件和成品放在本期项目文件夹里（`<片子文件夹>/<项目名>/02_制作/自动剪辑/`，2026-10-23 起；`~/Documents/` 下是早期位置）。

**做项目**：用户说“自动剪辑”“按烟道那条的做法剪”“给这条口播做卡点动画和字幕”，或要改审核线上的字幕、导出 4K 时，完整读取 `skill/thinkcut-edit/SKILL.md` 并严格照做，用户不必点名 Skill。各项样式由用户逐条定过，不要自行改动。

**分工边界**：
- 只剪口播（选重录、气口、字幕校对、交付主线）用 `thinkcut-edit「剪口播」`。
- 在实拍素材库里配 B-roll 用 `thinkcut-edit「配 B-roll」`。
- 花字用 `thinkcut-edit「花字音效」`。
- 章节导航条由 `thinkcut-edit「章节导航」` 出。

本能力只读 thinkcut-edit「剪口播」 的产物，不改 thinkcut-edit「剪口播」 的代码。在达芬奇里只复制主线，不改主线。

**命令怎么跑**：所有命令都是 `python3 skill/thinkcut-edit/scripts/thinkcut_edit.py <命令> <项目文件夹>`，命令入口只有这一个；做项目的命令实际都由 Claude 跑，Codex 只用于生图（见下面两条）。从 shell 启动时始终加 `< /dev/null`；出 4K、拼整轨这类几分钟的任务放后台。
- `anim-*`、`review`、`subfix`、`snap`、`stills`、`export`、`set-format` 这些要开无头 Chrome 或连达芬奇的命令都由 Claude 跑，不交给 Codex（Codex 只生图，见下一条；它的沙盒里也起不来无头 Chrome、连不上达芬奇）。
- **Codex 只用于生图**（封面底图、示意图；2026-11-21 用户：“只有生图交给他吧，其他的建模，包括怎么做的方案，都我们用Claude来做 包括做动画都我们自己做”）。动画、建模、方案都由 Claude 自己或 Claude 子助手做，难的派 Opus 子助手；子助手能自己出样张自查。
- **给用户看的内容只在对话里说，或放 Claude 文档，不写成 MD 文件**（交付清单、目标、提速建议、方案说明、总结；用户只在明确要求时才要 MD）。程序要读的记录照写：`反馈记录.md`、`02_制作/<项目名>.md`、反馈单、`给架构审查_*.md`、问题台账。项目收尾检查会提醒 `02_制作` 下给用户看的清单类 MD。
- **默认用满电脑性能**：渲染、自检截图、抽帧、转码、字幕整轨默认并行（程序命令有 `--workers` 的就用）；截图类实测 12 路后瓶颈在显卡，不用更多。达芬奇的操作不并行，同一时间只让一个会话写达芬奇（程序有写入锁，第二个会被拦下并说明谁在用，见 references/达芬奇经验.md）。下一个项目不该有单路跑超过 5 分钟的截图或渲染命令，遇到就提反馈（2026-11-21 用户定）。

**接入新 Mac**：在本目录运行 `bash bin/setup_mac.sh`。它会检查依赖，并把 Skill 链接到 `~/.claude/skills/thinkcut-edit` 和 `~/.codex/skills/thinkcut-edit`。

## 经验回路

2026-11-11 起走 **thinkcut-feedback**（`skill/thinkcut-feedback/SKILL.md`）：用户说“反馈”或项目收尾时，做项目的会话把问题整理好（2026-11-22 起不和用户逐条确认），直接写成 `internal/经验/待审/YYYY-MM-DD_<片名>_反馈单_<反馈人>.md` 交给“架构审查”。反馈人写姓名，不写机器名。每次新建文件，不往已有文件里追加，免得两台 Mac 冲突。

做项目的会话只记录，不改规则。反馈单由架构审查看全局逐条定（改／并进已有条目／回给这个项目／不改，要用户拍板的攒到一次问），要改的按下节改，改完反馈单移进 `internal/经验/待审/_已处理/`，记进 `internal/经验/已采纳.md` 和 CHANGELOG，并更新总账 `internal/经验/问题台账.md`（编号、修法级别、验收标准、状态、每个项目的 3 个数；只有架构审查改它）。其他待审经验仍在用户说“整理经验”时汇总给用户勾选。

## 修改本共享能力：占位与存档

**在开发版改（2026-11-24 用户定：开发和使用分开）**：改本文件夹一律在开发版 `<开发版目录>/studio` 里做，不直接改使用版 `<程序目录>/studio`（用户做项目用的那一份，只在发版时才变）。下面的占位、测试、存档都在开发版里做；存档后使用版还没变，要让用户用上，由“架构审查”在用户同意后发版（开发版根目录 `python3 bin/release.py release --note "…"`，做法见根目录 `架构审查交接.md` 第 1b 节）。本文件和各说明里写的 `<程序目录>/...` 都是使用版的路径，在开发版干活时改的是开发版里同一个相对位置的文件。

本能力由“架构审查”会话维护（做项目的会话不改），用 git 存档。用户是非技术人员，git 操作由 AI 代做，用中文汇报。只用本能力做项目、不改代码或文档时，不受本节约束（交反馈单除外）。

**改之前先占位。** 修改任何文件之前，用占位小工具建占位：`python3 ../bin/placeholder.py take "修改人：改什么"`（程序目录 `bin/` 下，2026-11-21 起；它会记下是哪台 Mac、哪个会话）：
- 它说“占位还有效”：别的会话正在改。告诉用户里面写的修改人和修改内容，然后停止，不碰任何文件。
- 它说“占位已过期”并接手（建占位的会话已经不在了，或仓库 30 分钟没有任何改动；2026-11-21 用户定：过期的占位直接接手，不用等用户确认）：旧占位会自动挪进回收站。接手后先运行 `git status`，有对方留下的未存档改动就对着反馈单逐条审，对的留、半截的补完，单独存档，不混进本次存档，并告诉用户。
- 没有占位：直接建好。再运行 `git status`，发现不属于本次的未存档改动，要先告诉用户，不要混进本次存档。

**改完后存档。** 先运行 `bash bin/run_tests.sh`，显示“全部测试通过”才能继续：
1. 根目录 `VERSION` 改为 `YYYY-MM-DD.N`（当天第 N 次；2026-11-24 起全家一个版本号），在根目录 `CHANGELOG.md` 末尾加一句修改记录（本文件夹的 `CHANGELOG.md` 是合并前的记录，不再追加）。行为有变化时，同步更新 `SKILL.md`、references 和 `README.md`。
2. 运行 `git add -A`（整个程序目录是一个仓库，存档一次就把改到的各文件夹一起存了），核对暂存区里没有成品、缓存、项目目录、钥匙或占位文件，然后执行 `git commit --author "修改人 <none@local>" -m "MM-DD 修改人：一句话中文说明"`。
3. `python3 ../bin/placeholder.py release` 放掉占位，告诉用户新的版本号，并说明这时使用版还没变、发版后才用上。

测试没通过就不存档，说明情况，由用户决定继续还是放弃；放弃时只恢复本次的改动。无论结果如何，最后都放掉本次的占位（`release`），不动别人还有效的占位。

不得改写或删除已有的存档历史。用户说“退回到某个版本”时，用 `git revert` 生成新的存档，不用 `reset --hard`（在开发版做，再发版；要把使用版整个退回上一次发版之前，用开发版根目录 `python3 bin/release.py rollback`）。

改了样式（字幕、小圆圈、导航、画幅数值）时，要同步改 `samples/` 里的期望结果，并在根目录 CHANGELOG 写清楚“和之前的项目不再逐像素一致”。
